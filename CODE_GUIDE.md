## 1. Идея в одном абзаце

Есть герметичный объём газа (~100 мл). Оператор задаёт **уставку** — нужное давление, например «500 кПа». Прошивка измеряет реальное давление датчиком и крутит два «крана», чтобы давление вышло на уставку и **держалось** на ней, даже если объём потихоньку травит.

Всё это написано на **C** под **ESP-IDF** (среда для ESP32), поверх **FreeRTOS** (операционка реального времени, гоняет несколько «задач» как бы параллельно).

## 2. Главный принцип: два привода

Это ключ ко всему коду. Давлением управляют **два разных механизма**, и у каждого своя роль:

| Привод | Что задаёт | Чем управляется в коде |
|---|---|---|
| **Серво-кран** (RC-серва) | **НАПРАВЛЕНИЕ**: набирать / стравливать / закрыто | ШИМ, функция `set_servo_angle()` |
| **Игла на шаговом моторе** (NEMA17) | **СИЛУ потока**: насколько широко открыта щель | импульсы шага, функция `move_valve_absolute()` |

Почему так? Серва надёжно выбирает **одно из трёх положений**, но не умеет точно дозировать поток. Шаговик умеет очень точно (по «шагам») приоткрыть иглу, но сам не задаёт направление. Вместе они дают и направление, и точную дозу.

> **Запомни это правило — оно встречается в коде сотни раз:**
> **Открытие иглы — всегда положительное число (в шагах). Знак (вверх давление или вниз) задаёт серво.**

Три положения серво — это перечисление `ServoState` ([pressure_regulator.h](main/pressure_regulator.h)):

```c
typedef enum {
    SERVO_NEUTRAL,   // объём изолирован — держим
    SERVO_CHARGING,  // подаём давление (набор)
    SERVO_VENTING    // стравливаем (сброс)
} ServoState;
```

> ⚠️ **Осторожно с углами.** Реально исполняется функция `apply_servo()`, и она задаёт: `CHARGING → 0°`, `VENTING → 180°`, `NEUTRAL → 90°`. А текстовые комментарии в коде (в enum и в `set_servo_angle`) говорят наоборот (charging=180, vent=0) — **комментарии устарели/перепутаны, верь коду `apply_servo`**. Подробнее — в [разделе 12](#12-подводные-камни-и-неочевидности).

## 3. Философия управления: почему «скорость», а не «открытие»

Самый наивный регулятор: «давление сильно ниже цели → открой иглу пошире». Так делать **нельзя**: газ у самой цели течёт совсем не так, как вдалеке от неё, поэтому такой регулятор то проскакивает цель, то еле ползёт.

Поэтому здесь **каскад** — два вложенных регулятора:

```
  ┌──────────────────────────────────────────────────────────────┐
  │  ВНЕШНИЙ слой:  ошибка по давлению  →  ЖЕЛАЕМАЯ СКОРОСТЬ dP/dt │
  │  (далеко от цели — быстро; близко — медленно; это «умная рампа»)│
  │  функция: desired_rate_from_error()                            │
  └───────────────────────────────┬──────────────────────────────┘
                                  │ желаемая скорость, кПа/с
                                  ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  ВНУТРЕННИЙ PI:  держит РЕАЛЬНУЮ dP/dt равной желаемой         │
  │  выход = открытие иглы (шаги)                                  │
  │  функция: rate_control_step()                                  │
  └───────────────────────────────┬──────────────────────────────┘
                                  │ открытие иглы
                                  ▼
                 серво задаёт сторону, шаговик — величину
```

- **Внешний слой** (`desired_rate_from_error`) — это таблица «как далеко до цели → какую скорость разрешаем». Чем ближе к цели, тем меньше скорость, чтобы плавно подкрасться и не проскочить.
- **Внутренний PI** (`rate_control_step`) — подкручивает иглу, чтобы **реальная** скорость роста/падения давления совпала с заказанной.

> **Зачем именно скорость в середине?** Связь «открытие иглы → расход газа → скорость давления» почти **линейна** по всему диапазону. А нелинейность (у цели газ течёт слабее) автоматически гасится обратной связью по скорости. Поэтому коэффициенты внутреннего PI можно настроить **один раз** и не трогать.

**Но у самой цели всё ломается.** Нужная скорость становится крошечной (0.01–0.02 кПа/с), а это **меньше шума датчика** (±0.5 кПа/с). Регулятор по скорости начинает дёргаться. Поэтому у цели работа по скорости **выключается совсем**, и включаются другие приёмы — фазы HOLD и FINE (см. [раздел 8](#8-фазы-регулирования-внутри-running)).

Вот почему в коде так много «магических чисел» и мелких приёмов: каждый лечит конкретный сбой, замеченный на железе. Рядом с числом почти всегда есть комментарий «почему именно столько».

## 4. Карта программы: задачи и общие переменные

Прошивка — это несколько **задач FreeRTOS** (представь их как работников, каждый занят своим делом). Они общаются через несколько **общих переменных**.

```
┌───────────────────────────────────────────────────────────────────────┐
│                            ESP32 (FreeRTOS)                            │
│                                                                       │
│  ┌─────────────────────┐  меняет setpoint_kPa  ┌────────────────────┐ │
│  │ usb_uart_rx_task     │──────────────────────►│ pid_regulator_task │ │
│  │ команды по USB       │                       │  «МОЗГ». Каждые     │ │
│  └─────────────────────┘                       │  ~20 мс:           │ │
│  ┌─────────────────────┐  меняет setpoint_kPa  │  • читает давление  │ │
│  │ app_main (главный)   │──────────────────────►│  • выбирает фазу    │ │
│  │ забирает WiFi-команды│                       │  • двигает иглу/    │ │
│  └──────────┬──────────┘                       │    серво            │ │
│             │ исполняет                         └─────────┬──────────┘ │
│  ┌──────────▼──────────┐                                  │ читает     │
│  │ WiFi + TCP сервер   │   обновляет pressure1_kPa        ▼            │
│  │ (несколько задач)   │   ┌────────────────────┐  ┌────────────────┐ │
│  └─────────────────────┘   │ таймер датчика 50мс│─►│ display_update │ │
│                            │ (опрос давления)   │  │ _task (экран)  │ │
│                            └────────────────────┘  └────────────────┘ │
└───────────────────────────────────────────────────────────────────────┘
```

**Общие переменные** (объявлены в [config.h](main/config.h), определены в [config.c](main/config.c)):

| Переменная | Кто пишет | Кто читает | Смысл |
|---|---|---|---|
| `setpoint_kPa` | команды (`set`/`psf`/…) | регулятор | **уставка** — какое давление держать |
| `fast_mode` | команды | регулятор | `true` = быстрый режим (агрессивнее) |
| `pressure1_kPa` | таймер датчика | все | **текущее давление** с датчика |
| `current_valve_position` | приводы | все | положение иглы в шагах (0 = закрыта) |
| `is_homing` | команда `vent` / запрос | регулятор | «нужно физически стравить давление» |
| `is_calibrating` | калибровки/хоминг | регулятор, экран | «не трогай привод/SPI, идёт калибровка» |
| `requested_reg_state` | команды | регулятор | запрос смены состояния (idle/leak/…) |

> **Важная архитектурная деталь.** WiFi-команды **не исполняются в самой WiFi-задаче**. Она складывает их в очередь, а разбирает их `app_main` тем же кодом `handle_command()`, что и USB-команды. Так два источника команд не лезут в общие переменные одновременно → нет «гонок» (race conditions).

Все переменные, которые делят задачи, помечены `volatile` — это говорит компилятору «значение может измениться в любой момент из другого места, не кэшируй его».

## 5. Что происходит при включении (`app_main`)

Точка входа — `app_main()` в [main.c](main/main.c:298). Запускает всё по порядку:

```c
void app_main(void) {
    log_chip_serial();              // 1. печатает серийный номер чипа (из заводского MAC)
    LCD_init();                     // 2. инициализирует экран (SPI + шрифт из SPIFFS)
    pressure_ui_and_usb_init(&dev); // 3. поднимает приём команд по USB + запускает задачу экрана
    pressure_sensor_init();         // 4. запускает опрос датчика (таймер раз в 50 мс)
    hardware_setup_and_calibrate(); // 5. серво, пины шаговика, ХОМИНГ иглы, продувка
    regulator_start_task();         // 6. запускает задачу-регулятор (мозг)
    wifi_tcp_init();                // 7. поднимает WiFi (точка доступа) + TCP-сервер

    while (1) {                     // 8. вечный цикл: разбирает WiFi-команды
        while (wifi_tcp_poll_command(wcmd, sizeof(wcmd)))
            handle_command(wcmd);
        vTaskDelay(pdMS_TO_TICKS(20));
    }
}
```

Самое важное на шаге 5 (`hardware_setup_and_calibrate`, [config.c](main/config.c:36)):

1. **Хоминг иглы** (`calibrate_valve_home`): мотор медленно закручивает иглу до упора, пока драйвер не выдаст сигнал «авария/упор» на пин `PIN_ALARM`. Эта точка принимается за **ноль отсчёта** (`current_valve_position = 0`). Без хоминга мы не знаем, где физически находится игла.
2. **Продувка**: если в системе осталось давление выше 5 кПа — игла открывается настежь, давление стравливается в атмосферу, игла возвращается в ноль. Чтобы прибор стартовал с чистого нуля.

## 6. Сквозной сценарий: жизнь одной команды `set 5000`

Чтобы «сшить» все фазы в единую картину, проследим, что происходит после `set 5000` (медленный режим, высокая уставка):

1. **Команда принята.** `handle_command()` ([main.c](main/main.c:67)) видит `set `, парсит `5000`, вызывает `update_setpoint(5000, false)`. Та проверяет границы (0…4000) и пишет `setpoint_kPa = 5000`, `fast_mode = false`.

2. **Регулятор замечает новую уставку.** В `pid_regulator_task` ([pressure_regulator.c](main/pressure_regulator.c:1555)) видно, что `setpoint_kPa != active_setpoint` → `reset_controllers()` (чистим всё старое), `state = REG_STATE_RUNNING`.

3. **Фаза RATE — быстрый подход.** Давление 0, цель 5000, ошибка огромная. `desired_rate_from_error()` заказывает высокую скорость (до 100 кПа/с). `apply_servo(CHARGING)` — серво на набор. `rate_control_step()` (PI) открывает иглу так, чтобы реальная скорость совпала с заказанной. По мере приближения к цели заказанная скорость падает → игла прикрывается. Это «умная рампа подъезда».

4. **Подошли к цели → выход из RATE.** Как только `|ошибка| ≤ hold_enter_err` (0.8 кПа) — PID выключается **насовсем** (до новой уставки). `holding = true`. Игла садится на `seed` — позицию чуть ниже порога потока. Серво остаётся в наборе.

5. **Фаза SEARCH — поиск порога потока.** У иглы есть «мёртвый ход»: пока не приоткрылась до порога, газ не идёт. `hold_search_step()` быстро перебирает иглу вверх, пока давление не тронется. Нашли порог → запоминаем, доводим давление до цели.

6. **Фаза FINE — точное удержание.** Дошли набором → не «печатаем» давление, а ищем **равновесное приоткрытие**: такое, где приток газа ровно равен утечке. Перед этим — пауза + замер дрейфа (`FINE-SS`), чтобы понять, в какую сторону держать. Дальше игла стоит на равновесии, раз в 5 с подстраиваясь на 1 шаг против сноса. Давление замирает на 5000.

Если бы уставка была **низкой** (< 689 кПа), вместо FINE работала бы **серво-отсечка** (bang-bang): запечатано в покое, чуть ушли — короткий импульс, вернулись — снова запечатано. Почему так — в [разделе 8.5](#85-низкие-уставки-серво-отсечка-low_mode).

## 7. Автомат состояний

Регулятор всегда находится в одном из состояний `RegulatorState` ([pressure_regulator.h](main/pressure_regulator.h:117)). Главный цикл `pid_regulator_task` — это `switch` по этому состоянию.

```
            новая уставка (set X)
   ┌──────┐ ──────────────────────►  ┌────────────────────────────────┐
   │ IDLE │                          │           RUNNING              │
   │покой │ ◄──── idle/abort ────────│  активное регулирование         │
   └──┬───┘   (или цель достигнута)  │  фазы: RATE→SEARCH→HOLD→FINE   │
      │                              └────────────────────────────────┘
      │ vent (start_pressure_homing)
      ▼
   ┌─────────┐      команда leak     ┌──────────┐
   │ HOMING  │                       │  LEAK    │
   │стравить │                       │ тест     │
   │ всё     │                       │ утечки   │
   └─────────┘                       └──────────┘
```

| Состояние | Что делает | Чем запускается |
|---|---|---|
| `REG_STATE_IDLE` | Ничего не регулирует. Серво нейтраль, игла 0. Меряет дрейф в покое (`idle_speed`). | старт, `idle`/`abort`, после завершения других режимов |
| `REG_STATE_RUNNING` | Главный режим. Внутри переключает фазы (см. раздел 8). | новая уставка `set X` |
| `REG_STATE_HOMING` | Физически стравливает всё давление: серво VENT, игла настежь, ждёт падения, закрывает. **Блокирующий.** | `is_homing` (команда `vent`) |
| `REG_STATE_LEAK` | Разовый тест герметичности (накачать → запечатать → измерить падение → стравить). **Блокирующий.** | команда `leak` |

> «Блокирующий» = пока режим работает, главный цикл стоит в нём (крутит `vTaskDelay` кусками, чтобы не сработал watchdog). В это время `filtered_pressure` и прочие расчёты «заморожены» — поэтому в логах HOMING/LEAK берут **сырое** `pressure1_kPa` напрямую (его обновляет отдельный таймер датчика).

## 8. Фазы регулирования внутри RUNNING

Это сердце проекта. Когда `state == REG_STATE_RUNNING`, главный цикл в конце выбирает **одну из трёх функций-фаз** ([pressure_regulator.c](main/pressure_regulator.c:1786)):

```c
if (!reg.holding)          target_valve = run_rate_phase(...);   // ещё не у цели
else if (reg.fine_holding) target_valve = run_fine_phase(...);   // точное удержание
else                       target_valve = run_hold_phase(...);   // грубое удержание
```

То есть три флага решают, кто рулит:
- `holding == false` → **RATE** (ещё едем к цели);
- `holding == true && fine_holding == true` → **FINE** (точное удержание);
- `holding == true && fine_holding == false` → **HOLD** (грубое удержание / поиск порога).

Результат любой фазы — `target_valve` (желаемое открытие иглы). После выбора фазы цикл **ограничивает скорость** движения иглы (`max_step` за тик) и вызывает `move_valve_absolute()`.

Разберём каждую фазу.

### 8.1 RATE — быстрый подход (`run_rate_phase`)

[pressure_regulator.c:963](main/pressure_regulator.c:963). Работает, пока `holding == false`.

Логика:
1. Зафиксировать **сторону подхода** (`rate_approach_sign`): снизу едем (+1) или сверху (−1). Нужно быстрому режиму, чтобы поймать пересечение цели.
2. Проверить, **дошли ли**:
   - обычный режим: `|ошибка| ≤ hold_enter_err` **и по сырому, и по фильтру** (двойная проверка отсекает ложный спайк датчика);
   - быстрый режим: RATE ведёт **до самой точки**, отдаёт управление только когда давление **пересекло** цель.
3. Если **не дошли** — заказать скорость (`desired_rate_from_error`), поставить серво по знаку, открыть иглу (`rate_control_step`).
4. Если **дошли** — переключиться в HOLD: `holding = true`, посадить иглу на `seed` (подсказка порога), выбрать сторону коррекции по тому, с какой стороны цели мы сейчас.

Две вспомогательные функции этой фазы:

**`desired_rate_from_error(error, near, very_near)`** — таблица «ошибка → скорость»:

```
|ошибка| > 500 кПа → 100 кПа/с      |ошибка| > 16  → 3
|ошибка| > 250     → 50             |ошибка| > 5   → 1 (быстрый: 2)
|ошибка| > 80      → 20             |ошибка| > 1   → near (быстрый: 1)
|ошибка| > 30      → 10             иначе         → very_near (быстрый: 0.5)
```
Знак результата = направление (`+` набор, `−` сброс). Это и есть «педаль газа по расстоянию до цели».

**`rate_control_step(reg, desired, dt)`** — внутренний PI:
- `rate_err = |желаемая| − реальная_скорость_к_цели` (>0 — едем медленнее нужного);
- открытие иглы `= floor + Kp·rate_err + Ki·интеграл`;
- **анти-windup** (условная интеграция): не копим интеграл, если игла уже на упоре `valve_max` и просят открываться ещё — иначе «фантомный» интеграл потом секунды разматывается;
- **аварийный тормоз**: если летим к цели в 3–4.5 раза быстрее заказа — закрываем иглу на полном слю (`max_step` за тик) и синхронизируем интеграл с позицией. Спасает от удара магистрали на низком давлении.

### 8.2 SEARCH — поиск порога потока (`hold_search_step`)

[pressure_regulator.c:531](main/pressure_regulator.c:531). Вызывается из HOLD, когда доза направления ещё **не калибрована** (`dose_*_calibrated == false`).

Проблема: у иглы большой «мёртвый ход». Ползти к порогу по +2 шага за 5 с — это десятки секунд. Решение — **быстрый свип**:

```
фаза 0 ПОДГОН  → ждём, пока давление устаканится после RATE, «прибиваем»
                 фильтр P_filt к сырому (убираем лаг EMA)
фаза 1 ПЕРЕБОР → +search_step (1 шаг) раз в 0.2 с, пока P_filt не уйдёт
                 на search_dp_flow (0.05 кПа) над любым из чекпойнтов
                 кольца (лаги 0.25…1.0 с) → ПОТОК НАЙДЕН
фаза 2 ЕДЕМ    → держим иглу на найденной позиции, ждём, пока давление
   ДО ЦЕЛИ       дойдёт до (цель − search_target_back); там фиксируем
                 калибровку и держим иглу на (найденная − search_done_back)
```

Хитрость с «кольцом чекпойнтов» (`search_hist[]`): поток ищем не по скорости, а по **приросту давления** над несколькими точками в прошлом (лаги). Крутой старт ловит ближний лаг почти сразу, пологий — дальний. Порог по фиксированному ΔP для каждого интервала (а не по скорости) не даёт коротким окнам ловить шум.

### 8.3 HOLD — грубое удержание микродозами (`run_hold_phase`)

[pressure_regulator.c:1316](main/pressure_regulator.c:1316). Работает, когда `holding == true`, но `fine_holding == false`. Это большой `switch` по `servo_state`:

- **`SERVO_NEUTRAL`** (запечатано): игла на `floor`, газ не идёт. Если давление ушло за `hold_trig` от цели → выбрать сторону (набор/сброс) и стартовать эпизод. (В быстром режиме перед выбором стороны есть **пред-выдержка** `hold_presettle` — даём давлению отстояться, чтобы не словить ложное направление на транзиенте.)
- **`SERVO_CHARGING`** (идёт набор): если порог не калиброван → SEARCH; если направление удержания уже известно → довести дозой и войти в FINE ровно на цели; если это первый замер на уставку → дойти до точки замера (`цель − fine_ss_charge_offset`) и запустить паузу+замер дрейфа на 0.3 от цели.
- **`SERVO_VENTING`** (идёт сброс): зеркально набору. Плюс **выдержка перед открытием иглы** (`hold_vent_arming`): сначала серво доезжает в VENT и штуцер стравливается, и только потом открывается игла — иначе заряженный штуцер «дампит» давление в объём. А теперь простым а не иишнымм языком: короче в трубке перед игольчатым серво может быть большое остаточное давление от набора. Надо успеть его скинуть перед открытием игольчатого серво.

**Микродоза** (`hold_dose_step`, [pressure_regulator.c:436](main/pressure_regulator.c:436)): игла стоит на фиксированном открытии `step_holding_*`; раз в 5 с смотрим, **на сколько реально сдвинулось давление к цели** за окно, и чуть правим открытие:
- прошло меньше `dose_dp_slow` → приоткрыть (+trim);
- прошло больше `dose_dp_fast` → прикрыть (−trim);
- разгон/утечка → крупный шаг (`dose_trim_big`).

Скорость у цели измерить нельзя (тонет в шуме), а **само давление за 5 с** — видно. В этом вся идея HOLD. Плюс «мультиоконная» защита (`dose_hist[]`): разгон/утечку ловим по **любому** лагу сразу, не дожидаясь 5 с.
Опять таки, дельта Р смотрим фиксированное для любого временного интервала, не подстравиваю его под меньшее время, иначе шум даст ложное показание.

### 8.4 FINE — точное удержание (`run_fine_phase`)

[pressure_regulator.c:1082](main/pressure_regulator.c:1082). Включается флагом `hold_fine_enable` на высоких уставках, когда вышли на точку. Самый аккуратный режим.

Идея: вместо периодических подкачек найти **равновесное приоткрытие** — где приток через иглу ровно равен утечке — и просто стоять на нём. Серво при этом постоянно держит одно направление.

Внутри несколько подэтапов:

1. **Пауза + замер (`first_in_fine`, `FINE-SS`)**: после выхода на точку (вроде у меня там за 0.3 от точки) объём запечатывают (серво нейтраль, игла floor) и смотрят, **куда сам поплыл** P_filt за окно `fine_ss_period_us`. Это определяет направление удержания:
   - `dP < 0` (утекает) → держим **НАБОРОМ**;
   - `dP ≥ 0` (ползёт вверх) → держим **СБРОСОМ**;
   - `|dP|` пренебрежимо мал → объём держит сам, FINE не нужен, перекрываем всё.
   - Для прихода **набором** есть доп.проверка (`ss_from_charge`): первые 2.5 с — чистая пауза, дальше короткая проверка знака. Падаем → сразу набор; растём → обычный замер.
   сделано это чтобы когда сильно травит на 3000+кпа, то чтоб не успело много стравить
   - Результат запоминается в `fine_dir` (`fine_dir_known`), чтобы **повторно не замерять** (замер делается один раз на уставку).

2. **Дрейф-доводка (`hold_fine_step`, [pressure_regulator.c:733](main/pressure_regulator.c:733))**: раз в окно смотрим знак сноса давления и двигаем иглу на 1 шаг **против** него (росло → прикрыть, падало → приоткрыть). Окно с `|dP| < fine_eq_band` = «стоим», равновесие найдено и запомнено в `fine_eq_pos`. Если стоим, но мимо цели — **само равновесие** мягко двигаем на 1 шаг к цели (не рывком — рывок переливает).

3. **Защита `fine_drift_step`**: не толкаем давление **прочь** от цели (если уже ниже цели — не прикрываем; если выше — не приоткрываем). Естественный дрейф к цели при этом не глушим.

4. **Разворот направления (`fine_flip_floor`)**: если дрейф-алгоритм прикрыл иглу почти в ноль, а равновесия нет — значит держим не тем направлением. Разворачиваем серво и стартуем заново с маленького приоткрытия.

5. **Гейт FINE→HOLD**: если давление успокоилось, но стоит далеко от цели (`> 0.1`) — тонкой подстройкой не вытянуть, отдаём управление обычному HOLD. Трекер `fine_change` (сколько P_filt прошло за ~5 с) защищает от преждевременного выхода, пока равновесие ещё устаканивается.

### 8.5 Низкие уставки: серво-отсечка (`low_mode`)

Ниже `fine_min_setpoint` (689 кПа) точный FINE **не сходится**: равновесного приоткрытия нет (приток/утечка нестационарны из-за теплового крипа), игла уползает в floor, давление дрейфует. Поэтому там FINE выключается, и держим **bang-bang** (`low_mode`):

```
покой запечатан (серво нейтраль, игла floor)
   │  ушли за hold_trig_band (0.04) от цели
   ▼
импульс предкалиброванным шагом (набор / сброс)
   │  вернулись в hold_reseal_band (0.00 = ровно на цель)
   ▼
снова запечатано
```

Гистерезис `trig − reseal = 0.04` защищает от пинг-понга. И запечатывание, и срабатывание считаются по **отфильтрованному** давлению `error_filt` (раньше по сырому — латчилось на шуме, это и была «дрожь»).

## 9. Разбор по файлам и методам

Весь наш код — в папке [main/](main/). Папки `managed_components/`, `build/` — сторонние/сгенерированные, их не трогаем.

### 9.1 `main.c` — точка входа и команды

| Функция | Что делает |
|---|---|
| `app_main()` | Запуск всех подсистем по порядку (см. [раздел 5](#5-что-происходит-при-включении-app_main)) + вечный цикл разбора WiFi-команд. |
| `handle_command(str)` | **Разбор одной команды.** Ищет в строке подстроки (`set `, `idle`, `leak`…) и вызывает нужное действие. Общий для USB и WiFi. |
| `usb_uart_rx_task()` | Читает байты из USB (UART0), собирает строку, отдаёт в `handle_command`. |
| `respond(msg)` | Отправляет ответ **и** в USB, **и** всем WiFi-клиентам. |
| `get_chip_serial()` / `log_chip_serial()` | Серийный номер чипа из заводского MAC. |

> Порядок проверок в `handle_command` важен: `setrange` проверяется **раньше** `range` и `set `, потому что обе — её подстроки. Команды `set`/`pss`/`psf` не делают `return` — но это безопасно, т.к. их ключевые слова взаимоисключающи.

### 9.2 `config.c` / `config.h` — привод и «железо»

`config.h` хранит **номера пинов**, лимиты (`MAX_VALVE_STEPS`, диапазон ШИМ серво) и `extern`-объявления общих переменных. `config.c` — управление приводом:

| Функция | Что делает |
|---|---|
| `hardware_setup_and_calibrate()` | Настройка пинов, серво, затем **хоминг** иглы и **продувка** остаточного давления. |
| `calibrate_valve_home()` | Хоминг: закручивает иглу до упора (сигнал на `PIN_ALARM`), принимает точку за ноль. Жёсткий цикл импульсов с микро-паузами под watchdog. |
| `init_servo()` | Настройка аппаратного ШИМ (LEDC, таймер 0, канал 0, 50 Гц, 14 бит) для серво. |
| `reset_motor_driver()` | Импульс на `PIN_ENABLE` — сброс ошибки драйвера мотора. |
| `update_setpoint(set, fast)` | Безопасная установка уставки (кламп 0…4000) + режим. |

> Функции **движения** привода (`set_servo_angle`, `move_valve_absolute`, `start_pressure_homing`) физически лежат в `pressure_regulator.c`, но объявлены в `config.h` — потому что их зовут оба файла.

### 9.3 `pressure_regulator.c` / `.h` — ЯДРО

Самый большой и важный файл. Структура:

| Группа | Функции |
|---|---|
| **Приводы** | `set_servo_angle`, `move_valve_absolute`, `apply_servo`, `start_pressure_homing` |
| **Инициализация** | `regulator_init` (задаёт ВСЕ коэффициенты), `reset_controllers` (сброс при новой цели) |
| **Каскад** | `desired_rate_from_error` (внешний слой), `rate_control_step` (внутренний PI) |
| **HOLD** | `hold_dose_step` (микродоза), `dose_hist_tick` / `dose_window_reset` (окна) |
| **SEARCH** | `hold_search_step` (поиск порога потока) |
| **FINE** | `hold_fine_step`, `fine_drift_step`, `fine_seed_for_dir`, `update_fine_change_tracker` |
| **Сервис** | `leak` (тест утечки), `regulator_request_state` |

### 9.4 `pressure_sensor.c` / `.h` — датчик и экран

Датчик давления — отдельная микросхема, общается по **UART** (19200, чётность odd, опрос раз в 50 мс).

| Функция | Что делает |
|---|---|
| `pressure_sensor_init()` | Настройка UART1 + периодический таймер `timerCallback`. |
| `timerCallback()` | Раз в 50 мс: разобрать ответ на прошлый запрос + послать новый запрос давления. |
| `processIncomingData()` | Собирает байты UART в кадр (начало = `ACK 0x06`, длина 12). |
| `handleUART1ReceivedFrame()` | Проверяет кадр: адрес, XOR-чексумму, **байты заголовка** `frame[3]==0x07` и `frame[5]==0x00` (режут ложные кадры в ~65536 раз). |
| `handlePressureResponse1()` | Достаёт float-давление из кадра, отбраковывает NaN/переполнение/абсурд → пишет `pressure1_kPa`. |
| `performAdvancedZeroCalibration()` | **Обнуление датчика** (команда `zero` / кнопка Boot): говорит датчику «текущее давление = 0». |
| `ReadRange` / `SetRange` | Чтение/выбор рабочего диапазона датчика (служебные команды, делят UART → ставят опрос на паузу). |
| `pressure_task_pause/resume` | Пауза/возобновление фонового опроса на время служебной команды. |
| `display_update_task()` | Раз в 200 мс рисует на экране уставку, давление, счётчик ошибок; опрашивает кнопку Boot. |
| `LCD_init` / `pressure_ui_and_usb_init` | Инициализация экрана (SPIFFS+шрифт+SPI) и USB-приёма; запуск задач. |
| `regulator_start_task()` | Создаёт задачу `pid_regulator_task` (стек 4096, приоритет 5). |

> ⚠️ В `pressure_ui_and_usb_init` дескриптор `display_task_handle` присваивается задаче **USB-приёма**, а не задаче экрана (см. [раздел 12](#12-подводные-камни-и-неочевидности)).

### 9.5 `wifi_tcp.cpp` / `.h` — сеть

По умолчанию ESP32 поднимает **свою точку доступа** (AP). Параметры в `wifi_tcp.h`:

| Параметр | Значение |
|---|---|
| SSID | `ControllerN` |
| Пароль | `12345678` |
| IP | `192.168.4.1` |
| Порт | `3333` |
| Макс. клиентов | 3 |

Архитектура (несколько задач):
- `server_task` — слушает порт, принимает соединения, на каждое создаёт `client_task`.
- `client_task` — читает байты сокета, собирает строки, кладёт команды в очередь `s_cmd_queue`.
- `tcp_tx_task` — **единственное** место, которое пишет в сокеты: берёт строки из `s_tx_queue` и шлёт всем.
- `wifi_log_vprintf` — перехват **всех** логов (`ESP_LOGx`): дублирует их в WiFi. Поэтому телеметрия видна и в USB-мониторе, и по сети без правки самих логов.

| Публичная функция | Что делает |
|---|---|
| `wifi_tcp_init()` | NVS + WiFi (AP/STA) + сервер + перехват логов. |
| `wifi_tcp_send(msg)` | Кладёт строку в очередь на рассылку (неблокирующе, из любого потока). |
| `wifi_tcp_poll_command(out)` | Достаёт одну команду из очереди (зовёт `app_main`). |

> **Почему так разнесено?** Раньше `send()` звался под мьютексом прямо из лог-хука — и при шторме переподключений система намертво вешалась (взаимная блокировка). Теперь отправка изолирована в одной задаче, а очереди неблокирующие. Подробности — в комментарии у `wifi_tcp_send`.

### 9.6 `st7789.c` / `.h` и `fontx.c` / `.h` — экран и шрифт

Это **драйвер дисплея ST7789** по SPI и работа со шрифтами формата FONTX. По сути — стандартная библиотека (рисование пикселей, линий, фигур, текста), её обычно не трогают.

- `st7789.h`: структура `TFT_t` (состояние дисплея), макросы цветов (`rgb565`), прототипы `lcdDraw*`.
- `fontx.h`: структура `FontxFile`, функции загрузки/рендера символов.

Из прикладного кода зовут в основном `lcdDrawString`, `lcdDrawFinish`, `lcdFillScreen`, `lcdDrawRect/Line`. Шрифты лежат в `fonts/` и зашиваются в раздел `storage1` при сборке (см. `spiffs_create_partition_image` в [CMakeLists.txt](CMakeLists.txt)).

## 10. Справочник переменных (зачем нужна каждая)

Здесь разобрана структура **`PressureRegulator`** — это «вся память» регулятора. Поля сгруппированы по смыслу. Колонка «зачем» отвечает на вопрос *почему без этого поля нельзя*.

### 10.1 Общее состояние

| Поле | Зачем нужно |
|---|---|
| `state` | Текущее состояние автомата (IDLE/RUNNING/HOMING/LEAK). |
| `servo_state` | Кэш положения серво — чтобы дёргать ШИМ только при **смене** (а не каждый тик). |
| `active_setpoint` | Уставка, на которой реально работаем. Сравнение с `setpoint_kPa` ловит **смену цели**. |

### 10.2 Измерение скорости и фильтры

| Поле | Зачем нужно |
|---|---|
| `prev_pressure` | Давление на прошлом **свежем** отсчёте — база для dP/dt. |
| `last_pressure_us` | Время прошлого свежего отсчёта — для честного деления на dt (датчик обновляется раз в 50 мс, цикл быстрее). |
| `raw_rate` | Сырая dP/dt — только для лога/диагностики. |
| `filtered_rate` | Сглаженная dP/dt (EMA) — по ней работает RATE. |
| `rate_filter_alpha` | Сила сглаживания скорости (0.8 — сильное, т.к. dP/dt очень шумная). |
| `filtered_pressure` | Сглаженное давление (EMA) — пороговые решения в HOLD/FINE по нему (сырое латчит на шуме). |
| `press_filter_alpha` | Сила сглаживания давления (0.8). |
| `glitch_skips` | Счётчик подряд отброшенных «битых» отсчётов — анти-залипание (не более `PRESS_GLITCH_MAX`). |

### 10.3 Внутренний PI по скорости

| Поле | Зачем нужно |
|---|---|
| `rate_kp` | Реакция на отклонение скорости (шаги на кПа/с). |
| `rate_ki` | Набор стационарного открытия (убирает постоянный недобор скорости). |
| `rate_integral` | Накопитель интегральной части (всегда ≥ 0). |
| `rate_integral_max` | Потолок интегратора (страховочный анти-windup). |

### 10.4 Порог шума / «дошли»

| Поле | Зачем нужно |
|---|---|
| `sensor_noise_delta` | Дрожание датчика в покое (~0.22 кПа). Двойная роль: порог «дошли» и желаемая скорость у самой цели. |
| `sensor_noise_delta_filt` | То же, но для фильтрованного давления (0.01) — порог «дошли РОВНО на цели» в FINE-входе. |

### 10.5 Грубое удержание (HOLD) и микродозы

| Поле | Зачем нужно |
|---|---|
| `holding` | Флаг «фаза HOLD» (PID выключен до новой уставки). |
| `hold_enter_err` | `|ошибка| ≤ этого` → выходим из RATE в HOLD. |
| `hold_exit_err` | В HOLD `|ошибка| >` этого → микродозой не вытянуть, назад в RATE (гистерезис). |

## 11. Команды управления (точный список из кода)

Команды шлются по **USB** (115200) или **WiFi** (порт 3333), по одной в строку, регистр не важен. Разбирает `handle_command` ([main.c:67](main/main.c:67)).

| Команда | Что делает | Куда ведёт в коде |
|---|---|---|
| `set X` | Уставка = X кПа, **медленный** режим | `update_setpoint(X, false)` |
| `pss X` | То же, что `set X` (алиас) | `update_setpoint(X, false)` |
| `psf X` | Уставка = X кПа, **быстрый** режим (`fast_mode=true`) | `update_setpoint(X, true)` |
| `idle` / `abort` | Остановить регулирование (серво нейтраль, игла 0) | `REG_STATE_IDLE` |
| `leak` | Тест утечки (накачать → запечатать → измерить → стравить) | `REG_STATE_LEAK` |
| `vent` | **Физически стравить** всё давление | `start_pressure_homing()` |
| `home` | Заново найти механический ноль иглы (хоминг) | `calibrate_valve_home()` |
| `zero` | **Обнулить датчик** (текущее давление = 0) ⚠️ только на атмосфере | `performAdvancedZeroCalibration()` |
| `sn` | Показать серийный номер чипа | `get_chip_serial()` |
| `ser 1 A` | Вручную повернуть серво на угол A (0…180°), для тестов | `set_servo_angle(A)` |
| `range [N]` | Прочитать рабочий диапазон датчика | `ReadRange()` |
| `setrange N` | Выбрать рабочий диапазон датчика (0…4) | `SetRange()` |

> Примечание: в старом [README.md](README.md) упоминается команда `reset` для сброса давления — в коде её **нет**, физический сброс делает `vent`. Это руководство описывает фактический код.

## 12. Подводные камни и неочевидности

Места, где новичок (и автор) могут споткнуться. Перечислено честно, по факту чтения кода.

1. **Углы серво в комментариях перепутаны.** Исполняется `apply_servo()`: `CHARGING → 0°`, `VENTING → 180°`, `NEUTRAL → 90°` (это подтверждается и продувкой в `config.c`, где атмосфера = 180°). Комментарии в `enum ServoState` и в `set_servo_angle` говорят обратное (charging=180, vent=0) — **не верь им, верь `apply_servo`**.

2. **`display_task_handle` указывает не на ту задачу.** В `pressure_ui_and_usb_init` ([pressure_sensor.c:443](main/pressure_sensor.c:443)) этот хэндл получает задача **USB-приёма** (`usb_uart_rx_task`), а реальная задача экрана (`display_update_task`) создаётся с `NULL`. Поэтому `vTaskSuspend(display_task_handle)` во время продувки приостанавливает **приём команд**, а не отрисовку. Похоже на ошибку именования — если будешь трогать этот код, имей в виду.

3. **Команда `home` блокирует задачу, в которой выполнена.** `calibrate_valve_home()` зовётся прямо из `handle_command` (т.е. из `usb_uart_rx_task` или `app_main`) и крутится до конца хоминга. На это время приём команд из того же источника замирает. (Физический сброс `vent`, наоборот, идёт через флаг `is_homing` и исполняется в задаче регулятора.)

4. **Много ВРУЧНУЮ подобранных чисел.** Почти все пороги в `regulator_init` подобраны под конкретное железо (объём ~100 мл, конкретная игла/датчик). Менять их наугад нельзя — рядом в комментариях написано, какой сбой лечит каждое значение. На другом железе (другой объём, датчик, игла) их придётся перенастраивать.

5. **`fine_dev_guard = 0.00f` и хардкоды в `fine_drift_step`.** В коде есть честно помеченный «отвратительный хардкод» (`if (trim <= -4) trim = -3;`) и поля, чьи значения автор ещё подбирает (видно по комментариям «было… теперь пробую…»). Это рабочая зона настройки, а не финал.

6. **Логи — это интерфейс отладки.** Строки вида `ЗАДАЧА ЗАВЕРШЕНА, УДЕРЖАНИЕ ПОЗИЦИИ`, метки фаз (`RATE`/`SEARCH`/`HOLD`/`FINE`/`FINE-SS`) и `P_filt=` в логах используются для анализа (в т.ч. внешним парсером). Не переименовывай их бездумно.

7. **`factory`-раздел всего 1 МБ.** В [partitions.csv](partitions.csv) приложение занимает раздел `factory` размером 1 МБ. С добавленным WiFi образ может приблизиться к лимиту — при сборке следи за размером.

> Пункты 1, 2 и 7 — кандидаты на исправление. Если хочешь, могу оформить их отдельными задачами/правками.

## 14. Словарь терминов

- **Уставка (setpoint)** — целевое давление, к которому стремимся (кПа).
- **Ошибка (error)** — `уставка − давление`. Положительная = ниже цели (надо набирать).
- **кПа** — килопаскаль. Атмосфера ≈ 101 кПа.
- **dP/dt** — скорость изменения давления, кПа/с.
- **PI / PID-регулятор** — алгоритм, сводящий ошибку к нулю. **P** — правка пропорционально ошибке; **I** — накапливает ошибку, убирает постоянный недобор; **D** здесь почти не используется (отсюда «PI»).
- **Каскад** — два вложенных регулятора: внешний задаёт скорость, внутренний её достигает иглой.
- **Шаг (step)** — минимальное перемещение шаговика. Открытие иглы меряется в шагах.
- **Хоминг (homing)** — поиск опорного нуля механики (игла до упора).
- **Мёртвый ход / порог потока (cracking point)** — открытие иглы, ниже которого газ не течёт (`valve_flow_floor`).
- **EMA** — экспоненциальное скользящее среднее: `новое = α·старое + (1−α)·свежее`. Сглаживает шум.
- **Микродоза** — короткий импульс набора/сброса фиксированным открытием у самой цели (HOLD).
- **Равновесное приоткрытие** — открытие иглы, где приток = утечке; давление стоит без подкачек (FINE).
- **Дрейф** — медленный самопроизвольный уход давления в покое (утечка или тепловой крип).
- **UART** — последовательная связь «по двум проводам» (датчик, USB).
- **SPI** — быстрая последовательная шина (экран).
- **AP / STA** — режимы WiFi: AP (сама раздаёт сеть) / STA (подключается к чужой).
- **FreeRTOS** — операционка реального времени; гоняет «задачи» параллельно.
- **GPIO** — программно управляемая ножка чипа.
- **ШИМ (PWM)** — «дозирование» сигнала включением-выключением; им задаётся угол серво.
- **Watchdog** — сторожевой таймер: перезагрузит чип, если задача надолго «зависла». Отсюда `vTaskDelay`-кусочки в длинных циклах.
